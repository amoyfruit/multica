Every time an agent starts working, Multica creates a **run**. It records what triggered the work, which agent it went to, how far it has progressed, and whether it ultimately succeeded.

## Issues and runs

An issue holds the goal, discussion, assignee, and final status of a piece of work; a run records one agent execution against that work.

| | Issue | Run |
| --- | --- | --- |
| What it records | A piece of work moving forward | One agent run |
| How long it lasts | Can be discussed, amended, and reassigned repeatedly | From trigger until completion, failure, or cancellation |
| Cardinality | One issue can span many runs | Every run gets its own record |

So the same issue can be handed to different agents in turn, or run again after a failure. Each execution produces a new run record; earlier records are never overwritten.

## Trigger sources

Any of the following can trigger a run:

- Assigning an issue to an agent or a squad.
- Mentioning an agent in a comment.
- Sending a message to an agent in chat.
- An Autopilot firing on a schedule or from an external event.

Different entry points provide different context, but execution works the same way: Multica creates a run, a runtime claims it, and the runtime invokes the AI coding tool the agent is configured with.

## Execution lifecycle

A run typically moves through these states:

| State | Meaning |
| --- | --- |
| `deferred` | Scheduled to fire later; enters the queue at the appointed time |
| `queued` | Waiting for a runtime to claim it |
| `dispatched` | A runtime has claimed it and is starting the AI coding tool |
| `waiting_local_directory` | The target local directory is held by another run; waiting for the directory lock to release |
| `running` | The AI coding tool is executing |
| `completed` | The run finished normally |
| `failed` | The run errored or was interrupted |
| `cancelled` | The run was stopped manually |

When the runtime is online, a new run usually starts quickly; if the runtime goes offline after the run enters the queue, the run stays queued until it recovers. Queued work is not expired for waiting too long — a runtime that keeps heartbeating is busy, not gone, so its backlog is allowed to drain however long that takes. A queued run fails only when **both** are true: its runtime has been silent past the reconnect grace, **and** the run itself has been queued that long. The second condition matters when you assign work to a machine that is already asleep — the run still gets a full grace for you to bring it back, rather than failing straight away.

<Callout type="info">
If the system already knows the target runtime is offline before triggering, some immediate actions report that the run cannot start right now instead of creating a run nothing can claim.
</Callout>

A runtime with a healthy heartbeat can execute long runs; the server never force-ends a run just because it has been running for a while. The runtime decides whether the process has stalled based on actual activity; see [Environment variables](/environment-variables#daemon-configuration) for the relevant settings.

## Viewing run history

Every run an issue produces is listed in the **Execution log** section of the issue's right sidebar — not on a separate page or tab. The section is expanded by default: active runs stay pinned at the top, and finished ones sit behind **Show past runs (N)**. Each row shows the trigger source, the executing agent, the state, and timing. If you don't see the section, open the sidebar with the panel button in the issue header; on narrow screens it starts collapsed.

The log updates over the realtime connection while the page stays open — new runs, status changes, and the agent's comments appear without a manual reload.

While an agent is working, the issue header also carries a live chip such as "Engineer is working". Hovering it shows the same active runs, so you can check progress without leaving the page.

From here you can:

- Click **View transcript** on a row to see the agent's messages, tool calls, and error output. For a run still in progress the transcript keeps streaming while the dialog stays open, and a **Newest first** toggle flips the event order.
- Stop runs that are deferred, queued, starting, waiting for a local directory, or running.
- Retry a failed or cancelled run.

Changing an issue's assignee or status does not stop a run that has already started. To interrupt one, stop the corresponding run in the execution log. Active runs are cancelled along with an issue only when the issue is deleted.
</Callout>

## Failures and automatic retries

Transient faults — a runtime going briefly offline, a daemon restart, an execution timeout, or a network interruption in the AI coding tool — can trigger an automatic retry. A regular run executes at most twice by default; tool network interruptions get up to three attempts.

Errors returned by the agent itself are usually not retried automatically. Expired credentials, exhausted quota, misconfiguration, or a model unable to complete the request all need the cause fixed first, followed by a manual retry.

An Autopilot's **run only** mode does not retry automatically, to avoid overlapping with the next scheduled run. The **create issue** mode produces regular issue runs, so infrastructure failures still retry under the rules above. Both modes show their final result in the Autopilot run history.

When an issue has no other active run and no new retry waiting to run, a failure moves an `in_progress` issue back to `todo`.

## Failure reason reference

The failure reasons shown in the execution log and usage stats fall into two groups: unprefixed reason codes are recorded by the platform; `agent_error.*` codes are classified from the AI coding tool's own errors.

**Platform side**

| Reason | Meaning | What to do |
| --- | --- | --- |
| `runtime_offline` | The runtime went offline during the run | Restore the runtime and retry; see [Daemon and runtimes](/daemon-runtimes) |
| `queued_expired` | The runtime stopped heartbeating for longer than the reconnect grace, and the run had also been queued that long | Confirm the runtime is online, then retry |
| `runtime_recovery` | The daemon reclaimed an interrupted run after restarting | Retry directly |
| `environment_prepare_failed` | The daemon could not set up the execution environment for this run — its working directory, or the local runtime config written into it | Read the raw error to see which step failed, then check that machine: disk space, permissions, a directory still in use, or the AI coding tool's local config |
| `cancelled` | Stopped manually, or cancelled along with an archive or delete | Nothing to do |
| `timeout` | Exceeded the daemon's configured execution time limit | Narrow the issue scope, or adjust the daemon's `agent_timeout` |
| `iteration_limit` | Hit the iteration cap for a run | Narrow the issue scope |
| `agent_blocked` | The agent reported it cannot proceed | Provide what its comment asked for |
| `api_invalid_request` | The platform API rejected an invalid request | Retry; report the problem if it recurs |
| `no_deliverable` | The run finished but delivered nothing visible — no final output and no comment on the issue | Retries automatically on the same session; if it persists, the model is likely hitting its output limit — see small-model rules below |
| `codex_semantic_inactivity` | Codex produced no meaningful output for too long and was judged stalled | Retry, or adjust the Codex inactivity timeout |

**Tool side (`agent_error.*`, prefix omitted)**

| Reason | Meaning | What to do |
| --- | --- | --- |
| `provider_auth_or_access` | Model provider authentication failed or access denied (401/403) | Sign in again in that AI coding tool, or check the API key |
| `provider_quota_limit` | Quota or balance exhausted (402) | Top up or switch accounts |
| `provider_capacity_or_rate_limit` | Rate limited or out of capacity (429/529) | Retry later |
| `provider_server_error` | Model provider server error (5xx) | Retry later |
| `provider_network` | Network failure reaching the model provider | Retries automatically; check the executing machine's network if it persists |
| `model_not_found_or_unavailable` | The model does not exist or is currently unavailable | Pick an available model in the agent settings |
| `context_overflow` | Context exceeded the model window | Narrow the issue scope or reduce the input |
| `missing_config` | Required configuration such as an API key is missing | Fill in the agent's environment variables or the tool configuration |
| `runtime_missing_executable` | The AI coding tool's executable was not found | Reinstall the tool; see [Install AI coding tools](/install-agent-runtime) |
| `runtime_version_unsupported` | The AI coding tool version is too old | Upgrade the tool |
| `process_failure` | The tool process exited abnormally | Check the run record to locate the cause, then retry |
| `empty_or_unparseable_output` | The tool produced no output, or output that could not be parsed | Retry; check the tool installation if it recurs |
| `output_truncated` | The model's final turn was cut off at its output-token limit before producing any text — typical of small models with a low `max_tokens` | Retries automatically on the same session; raise the model's `max_tokens` or use a larger model |
| `agent_timeout` | The tool was terminated after going unresponsive for too long | Retry or narrow the issue scope |
| `unknown` | Unclassified failure | Check the raw error in the run record |

## Manual retry

Clicking the retry button on a row in the execution log invokes **the agent that handled that run at the time**. Even if the issue has since been reassigned, the retry does not switch to the new assignee.

A retry keeps the files the previous run already wrote to the local directory whenever possible. If the original session is still safe and the same runtime claims the retry, it also continues the previous session. Errors that poison the session, such as context overflow or invalid requests, start a new session on top of the original working directory instead. When the original directory no longer exists, a fresh working directory is used.

You can also rerun the current issue from the CLI:

```bash
multica issue rerun <issue-id>
```

This form does not point at a specific past run, so it uses the issue's current agent assignee and starts with a fresh session and working directory.

## Run completion and issue completion

`completed` only means this particular run ended normally — it does not confirm the issue's goal has been met. You can still review the result, keep discussing, add requirements, or trigger the agent again.

Whether an issue is done is judged by the actual progress of the work and the issue's status.

## Running small local models

Small local models (low `max_tokens`, small context window) fail in three distinct ways, and all three used to end as `completed` runs with nothing delivered:

1. **Output truncation** — the generation is cut at the output limit (`stop_reason: length`) on the very turn that would have posted the deliverable.
2. **Context overflow on resume** — re-triggering the agent on the same issue resumes the prior session; on an issue with heavy history the accumulated prompt exceeds the model's window and the request is rejected with a 400.
3. **Degenerate generations** — the model ends the run with a one- or two-token reply.

The platform now fails and auto-retries the first and third shapes (`no_deliverable`, `output_truncated`), and the second shape retires the oversized session from the resume pointer so the next run starts fresh. To keep small-model agents productive regardless, add these operating rules to the agent's instructions:

- Never emit more than ~3000 characters of new text in a single tool call or a single reply.
- Build long deliverables in a file across many small steps: a short first `write`, then short append edits of a few KB each. Only append the new chunk; never re-emit the whole file.
- Post the finished file with a single `multica issue comment add --content-file` call and confirm the post succeeded before ending the turn.
- When a resumed run fails with `context_overflow` or `api_invalid_request`, dispatch the work as a fresh sub-issue (new session) instead of re-triggering the same issue.
- Raise the inference server's `max_tokens` for the model where possible — a degenerate cap (a few dozen tokens) makes every retry reproduce the same truncation until the attempt budget runs out.

## State and timeout quick reference

The numbers below reflect the server's default configuration, for quick cross-checking while troubleshooting.

| State | Meaning | Timeout and consequence |
| --- | --- | --- |
| `deferred` | Scheduled to fire later | Enters `queued` at the scheduled time, then the rules below apply |
| `queued` | Waiting for a runtime to claim it | Waits as long as its runtime keeps heartbeating, and in every case for at least one reconnect grace after being queued; fails only when both windows have passed, and is not retried automatically |
| `dispatched` | Claimed; the tool is starting | Treated as failed after more than **5 minutes** in this state |
| `waiting_local_directory` | Waiting for the local directory lock to release | No timeout of its own; returns to the startup flow once the directory is released |
| `running` | The AI coding tool is executing | No fixed duration cap; liveness follows the runtime heartbeat — one every 15 seconds; a runtime that loses its heartbeat is marked offline within about 3 minutes at the latest, and its runs fail with it |

Automatic retry covers only the transient faults below, and only applies to runs attached to an issue or a chat (excluding the Autopilot **run only** mode):

| Auto-retryable failure reason | Attempt ceiling |
| --- | --- |
| Runtime offline | 2 by default (first run + 1 retry) |
| Reclaimed after a daemon restart | 2 by default |
| Platform-judged execution timeout | 2 by default |
| Codex stalled with no meaningful output | 2 by default |
| Skill bundle download failure | 2 by default (the agent process has not started at this point; already-downloaded bundles come from the local cache) |
| No visible deliverable at completion | 2 by default (the retry resumes the same session and continues the truncated turn) |
| Final turn truncated at the output limit | 2 by default (same retry semantics as no visible deliverable) |
| Tool network interruption | Up to 3; the final attempt starts after a delay of about 5 seconds |

All other failure reasons (auth, quota, configuration, model, and so on) never retry automatically; fix the cause first, then retry manually.
